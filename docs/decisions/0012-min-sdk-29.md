# 12. `minSdk` 29 for the envelope-encryption release, on the feature branch only

Date: 2026-10-21

Status: Accepted — applies to `feature/envelope-encryption`; `master` keeps `minSdk` 24 until the
final merge. Amends the API ranges of [ADR-0011](0011-envelope-encryption-spike-results.md).

## Context

The envelope-encryption design ([docs/design/envelope-encryption.md](../design/envelope-encryption.md))
carried three branches that exist only for API 24–28: the SHA-1 PBKDF2 variant for API 24–25
(`PBKDF2WithHmacSHA256` is API 26+), the separate `KeyguardManager` credential Activity that
androidx.biometric 1.1.0 uses on API ≤ 28, and the API 24 Keystore quirks of ADR-0011 S2/S9. The
same levels are where biometric login had silently stopped working in production: `androidx.core`
≥ 1.18 stubs `FingerprintManagerCompat`, which `androidx.biometric:1.1.0` still routes through on
API ≤ 28 ([#299](https://github.com/Ni3verma/Safe-Box/issues/299)); the only library line without
that dependency is `androidx.biometric` 1.4.0, alpha since 2021's 1.1.0 was the last stable.

Play Console → Statistics, *Install base* and *Installed audience* by Android version, exported on
2026-10-21 for 23 Jul – 19 Oct 2026 (89 days). Android 7.0 does not appear in the dimension picker
at all, i.e. zero devices in the period. Installed audience (unique users), 14-day mean to 19 Oct,
total ≈ 1 113:

| Version | API | users / day | share | cumulative ≤ |
|---|---|---|---|---|
| 7.1 | 25 | 2.3 | 0.2 % | 0.2 % |
| 8.0 | 26 | 4.5 | 0.4 % | 0.6 % |
| 8.1 | 27 | 8.1 | 0.7 % | 1.3 % |
| 9 | 28 | 24.1 | 2.2 % | **3.5 %** (≈ 39 users) |
| 10 | 29 | 54.7 | 4.9 % | **8.4 %** (≈ 94 users) |
| 11 | 30 | 75.7 | 6.8 % | 15.2 % (≈ 170 users) |

Install base (unique devices) gives the same picture: 3.7 % / 8.9 % / 15.7 %. Over the 89 days
Android 10 was flat (47 → 53 users) while Android 11 fell 16 % (89 → 75): Android 10 devices are
end-of-life and leave only by replacement, so a later cut at 30 would not get cheaper by waiting.
Installed audience is an upper bound on the *active* share of old versions; GA `login_success` by
OS version (MR T) will confirm it once the next release ships, but is not needed for the decision.

## Decision

1. **`minSdk` 29** in `:app` and `:upgrade-test`, committed to `feature/envelope-encryption` as its
   first child MR. The API 24–28 code and design branches are removed on that branch.
2. **Not 30.** It would strand 8.4 % of users instead of 3.5 % and its only design gain is deleting
   the time-bound `KEK_Device` recovery path for Android 10 (≈ 50 production lines, ≈ 100 test
   lines, one manual API 29 matrix row — design §2.3, §6.7). The design already decides that path's
   fate from the `forgot_password_click` OS split at MR 6: if Android 10 recovery usage is ≈ 0,
   recovery becomes API 30+ and Android 10 maps to the existing recovery-not-set-up state; otherwise
   the time-bound key stays for 29 only. Nobody is stranded for a code path either way.
3. **Not `master`.** Until the feature branch merges, any interim release from `master` must keep
   reaching Android 7–9 users, so the bump ships only with the envelope release (design §9.1
   rule 4). `master`'s copies of the design, `PROJECT_FACTS.md` and the skills therefore still
   describe `minSdk` 24; the feature branch's copies overwrite them at the final merge.
4. **`androidx.biometric` stays at 1.1.0.** On API 29+ it uses the framework prompt exclusively
   (`isManagingDeviceCredentialButton()` is `SDK_INT <= P` in the 1.1.0 sources), so #299 is moot
   and the alpha 1.4.0 line is not adopted. The issue closes with the final merge.

## Consequences

- Code removed with the bump: the `SDK_INT >= O` channel guard in `Utils.makeStatusNotification`,
  the pre-Pie `setPrimaryClip` fallback in `ClipboardClearWorker`, the `SDK_INT >= P` guard on
  `FEATURE_STRONGBOX_KEYSTORE` in `AndroidDeviceSecurityStatus`; `mipmap-anydpi-v26` is now
  `mipmap-anydpi`. The #280 `getAllowedAuthenticators` matrix keeps its `sdkInt < R` row because
  API 29 still rejects `BIOMETRIC_STRONG or DEVICE_CREDENTIAL` (#279).
- Design: KDF is `PBKDF2WithHmacSHA256` only with a single `PBKDF2_ITERATIONS` (the `<algorithm>`
  field of `kdf_params` stays for agility); the time-bound `KEK_Device` path, `T`, decision 3 and
  the §1.3 residual are scoped to API 29; §12.1 loses its API 24 and 28 rows; the S1 numbers of
  ADR-0011 (measured on 24/28, the credential-Activity path) become the upper bound for the
  shorter in-prompt path of 29, so `T` = 5 s stands as a conservative value.
- Users on Android 7.1–9 keep the last compatible release, with the legacy encryption, and stop
  receiving updates after the envelope release; they cannot reinstall on a new device below
  Android 10. Play shows the app as incompatible to them.
- The API 24 and 28 emulator rows of ADR-0011 stay as evidence; nothing in them is re-measured.
